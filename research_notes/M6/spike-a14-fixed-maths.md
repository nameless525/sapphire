# Spike A14: how much of the fixed step's float maths traversal runs through

What M6 A14 had to answer before A15 starts (m6-plan §6, "Determinism where traversal touches the checksum"): which float operations climbing, gliding, swimming and the traversal moves will run inside the fixed step, which of them are already on the deterministic maths, which aren't, and what A15 must move first. Read from the code at e99cd54cb on 2026-11-27; nothing here was timed, and no cross-architecture run was made for it (the replays' x86-64 checksums come from CI as always).

## The scope of "deterministic" today

`sapphire_math::det` (`crates/sapphire_math/src/det.rs:1-12`) promises bit-identical replays **within an architecture**: every aarch64 build reproduces every other aarch64 run, and every x86-64 build every x86-64 run, which is why `tests/replays/` holds one checksum file for each. Bits *across* architectures are a non-goal except for what a bake writes. So the question for traversal is in two parts: whatever reaches the state checksum must be the same on every OS of one architecture (no C maths library, no address or hash order), and whatever a cook bakes must be the same on both.

## What traversal will run, and where it stands

**On the controller's path (`crates/sapphire_gameplay/src/controller/`): deterministic.** The capsule's moves, the ground and step probes and every slide are scalar `Vec3` arithmetic, `det` for anything transcendental (`ResolvedProfile::new`'s slope limit, `controller/profile.rs`), and `sapphire_physics`' sweeps and rays (`PhysicsWorld::cast_ray`, `cast_body`, `move_and_collide`) on parry3d with `enhanced-determinism` held off. Climbing's attach and re-cast (A16a), the ledge probes of a mantle (A15), a glide's height cast (A17) and a swim's floor ray (A19, through `WaterVolumes::at` and `floor_below`) are more of the same calls with a different filter (`Group::Climbable` for a climb's). They add casts, not a new kind of maths. What none of this proves is parry3d's own bits across architectures, which the physics checksum test (`crates/sapphire_physics/tests/checksum.rs`) pins per architecture.

**Root motion and warp: deterministic.** A move's root table is baked at cook time through `det` (`tools/sapphire_pipeline/src/moves.rs:238-319`) and read by scalar interpolation (`BakedTables::root_at`, `crates/sapphire_moves/src/lib.rs:519-529`); the warp that bends it toward a target is `det::rotate_y`, `wrap_angle` and `yaw_of_direction` over scalar `Vec3` (`crates/sapphire_gameplay/src/moves.rs:1251-1310`), horizontal only (`horizontal()`, line 1313). A15's vertical `max_rise` extends that function; it doesn't add a new kind of maths.

**`FixedBody` (`crates/sapphire_body_pose/src/graph/fixed_body.rs`): mostly pinned, with a float layer above.** The body runs in the step only for an actor a simulation binds to it (`crates/sapphire_gameplay/src/body/mod.rs:1-2`, the overhead contact route), and its state is in the checksum (`BodyAuthority::write_state`, same file). Its arithmetic goes through `PoseMath` (`crates/sapphire_body_pose/src/pose_math.rs:7-11`), whose `Pinned` arm the fixed owner sets (`graph/fixed.rs:63-64`, `character.rs:155-166`):

- **Already on `det` or scalar maths:** clip sampling (`sapphire_assets/src/clip.rs:484-499`, `sample.rs:42-58`), blending and additive layers (`blend.rs:110-197`), blend-space weights, inertia and the ground turn (`blend_space.rs:57`, `inertia.rs:84,97`, `policy.rs:157,208,219`), rig constraints (`constraints.rs:204-253`), the two-bone and aim solves' angles and turns (`ik/solve.rs:214-276,308-335`), feet, takeoff, footwork and look's rotations (`ik/feet.rs`, `ik/feet/takeoff.rs`, `ik/look.rs:227-289`), the root's placement (`fixed_body.rs:43-48`) and read interpolation (`motion.rs:178-183`).
- **Not routed: glam's SIMD affine types, by operator.** Forward kinematics (`model.rs:28-31`, `parent * local.to_affine3a()`), a solve's carry of what's below a turned joint (`ik/solve.rs:152-154`) and the pivot transform it's built from (`about`, `ik/solve.rs:170-172`), the parent's inverse in `translate` (`ik/solve.rs:145`), `Quat::from_mat3a` before a pinned normalize (`rotation_of`), and every `transform_point3` and `inverse` that turns a target or a probe into the model's space (`ik/mod.rs:279`, `ik/feet.rs:669-670` and on, `ik/footwork.rs:153-227`, `ik/authored_support.rs:223`, `ik/hands.rs:98`). These are `Affine3A`, `Mat3A` and `Vec3A` operators, which `det`'s own docs name as NEON on aarch64 and SSE2 on x86-64: the same within an architecture, unpinned across. The body's foot probes are the same `cast_ray` the controller uses (`body/mod.rs:43-48`, `ik/mod.rs:245-253`), filtered to `Group::World`.
- **The comment at `pose_math.rs:13-14`** keeps host maths to the `Legacy` arms and names "the remaining IK/FK debt": that's the layer above.

## So how much is debt

Within an architecture, none of it breaks a replay: the affine layer is the same code on the same CPU every time. It's debt in two senses. It isn't pinned across architectures, so nothing could ever bake from a solved pose, or compare a body's state between aarch64 and x86-64. And nothing tests it: `the_test_contents_hash_is_the_same_on_every_architecture` holds move data, not body state, and no test hashes a `FixedBody`'s state on two architectures.

Traversal's simulation half doesn't run through it. Climbing, gliding and swimming are the controller's modes, mantles and vaults are moves with baked tables, and none of them reads a solved pose in the step. The debt reaches traversal only where a pose would decide something the simulation keeps: A16b's limb probes along the face's normal, if they run in a bound `FixedBody` (its hands-within-3 cm test is presentation), or anything that ever lets a hand's or a foot's solved place move the capsule.

## What A15 must move first

1. **Nothing of `FixedBody`,** provided A15's mantle reads no pose in the step: its ledge probes stay on `PhysicsWorld::cast_ray` and `cast_body` from the controller, and its vertical warp stays inside `moves.rs`' scalar warp. A test that a bound body's state checksum doesn't depend on the traversal mode, once A5b's runtime reads `Traversal(Mode)`, would hold that line.
2. **Before A16b's limb probes run in a bound body:** forward kinematics and the carry (`model_of`, `SolvePose::carry`, `about`) onto a scalar affine with `det::quat_rotate`, then the inverses and `transform_point3` on the IK inputs' path (feet, look, footwork, authored support), then `hands::reach`'s grip before hand IK is turned on in the step (gameplay passes `weapon: None` today, `body/mod.rs:276`).
3. **A body-state hash across architectures,** like the move data's: the test that would show the affine layer moved, and the one to pin once it has.

## Not verified

Whether glam 0.33's `Affine3A` and `Mat3A` operators actually give the same bits on NEON and SSE2 here: the source reads as the same order of multiplies and adds with no fused multiply-add in the matrix paths, and a fused one in `Quat * Quat` and `Vec3A::lerp` on NEON, which the pinned arm avoids, but no run compared them. parry3d's bits across architectures. Whether climbing will want fixed point rather than `det` floats: nothing here suggests it, since every replay is held per architecture.
