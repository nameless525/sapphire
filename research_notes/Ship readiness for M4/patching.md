# Patching: chunking, signed manifests, download, atomic swap

A scout's read on 2026-11-10, web only, nothing built or run. Crate versions are from the crates.io API on 2026-11-10; everything else is from the linked pages or from memory of them, and is marked where it was not re-read today.

## 1. Chunking

- FastCDC (Xia et al., USENIX ATC 2016, https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia) claims about 10x the speed of Rabin-based CDC at near-equal dedup ratio, via a gear hash, skipping the region below the minimum size, and "normalized chunking" (two masks, tighter size spread). The 2020 follow-up (IEEE TPDS, "The Design of Fast Content-Defined Chunking for Data Deduplication Based Storage Systems") adds "rolling two bytes each time" for a further speedup. Not re-read today.
- `fastcdc` crate: 5.0.0 (crates.io, updated 2026-08-22). Its docs (https://docs.rs/fastcdc) have offered `v2016` and `v2020` modules with `FastCDC::new(&data, min, avg, max)` iterating `Chunk { offset, length, hash }` plus a `StreamCDC` over `Read`; whether 5.0 renamed anything is unverified. The crate documents min/avg/max limits (avg roughly 256 B to 4 MiB in v2020).
- Typical sizes: restic uses 512 KiB min / 1 MiB avg / 8 MiB max (https://restic.readthedocs.io/en/stable/100_references.html); casync defaults 16/64/256 KiB (https://github.com/systemd/casync). Not re-read today.
- ours: CDC exists to survive insertions shifting byte offsets. Our packs already cut each asset into independently compressed 64 KiB blocks with their own blake3, so an asset's unchanged blocks are already byte-stable and content-addressable. Fixed-size chunking keyed by block blake3 gets near-CDC reuse for free, except where an edit early in an asset shifts every later block's boundary (e.g. a mesh whose vertex buffer grows). CDC over the uncompressed asset, then compressing each chunk, would fix that; worth measuring on two real cooks before choosing.
- ours: the unit of download should be the stored (compressed) block, so the client never recompresses, and the pack can be reassembled byte-identically from blocks plus the TOC.
- Steam SteamPipe: Valve's docs say content is split into roughly 1 MB chunks, and recommend aligning/keeping file layout stable since changes are found per chunk (https://partner.steamgames.com/doc/sdk/uploading, "Building Efficient Depots"). Valve advises against compressing/encrypting packs whole for this reason. ours: our per-block compression is the right shape for this.
- Epic BuildPatchTool: manifests list files as sequences of chunk parts; chunks are ~1 MiB, found by a rolling hash so data shifts still match (https://dev.epicgames.com/documentation/en-us/unreal-engine/build-patch-tool-overview-for-unreal-engine — not re-read today).
- Riot RMAN: public write-up "Supercharging Data Delivery: The New League Patcher" (https://technology.riotgames.com/news/supercharging-data-delivery-new-league-patcher) describes content-defined chunks, bundled into larger "bundles" on the CDN, fetched with HTTP range requests; the manifest is flatbuffers. Not re-read today.
- Blizzard TACT/CASC: content addressed by MD5 ("content key" vs "encoding key"), files in BLTE-encoded archives with per-block compression, indices map keys to archive offsets (community docs: https://wowdev.wiki/TACT, https://wowdev.wiki/CASC). ours: closest to our existing pack design.
- ours: the Riot point matters for CDN cost: many small objects are expensive; serve packs or block bundles whole and fetch blocks by range.

## 2. Signed manifests and update security

- TUF spec (https://theupdateframework.github.io/specification/latest/): roles root (trust anchor, signs other roles' keys), targets (hashes and lengths of files), snapshot (versions of all targets metadata, stops mix-and-match), timestamp (short-expiry pointer to the latest snapshot, stops freeze). Attacks named include arbitrary software installation, rollback, indefinite freeze, endless data, extraneous dependencies, mix-and-match, slow retrieval, fast-forward, vulnerability to key compromise.
- Root rotation (spec §5.3): the client walks root N+1, N+2, ... each signed by a threshold of both the old and new root keys, then checks expiry.
- `tough` (AWS, https://github.com/awslabs/tough): 0.24.0, updated 2026-07-10, so maintained. `tuf` (rust-tuf, https://github.com/theupdateframework/rust-tuf): 0.2.0, last updated 2025-10-20; historically slow-moving. ours: `tough` is the one to evaluate if full TUF is wanted; it pulls an HTTP stack of its own (reqwest) that may not match ours, check before adopting.
- ours, minimal design for one publisher: (a) an embedded root public key list in the binary plus a signed root document that can name successor keys (one hop of TUF's rotation); (b) a manifest with a monotonically increasing version, an `expires` time, the list of packs with size and blake3 of TOC, and the block index; (c) client rejects version <= installed (rollback), rejects expired (freeze; needs a trusted-ish clock, tolerate skew), caps download length to manifest sizes (endless data); (d) a small separately signed "latest" pointer with short expiry if freeze matters. Signing the whole manifest once covers mix-and-match since everything is in one document.
- ours: the pack header's reserved signature block (scheme, key ID, 64 bytes) fits ed25519 exactly; signing the manifest is enough if every pack's TOC hash is in it.
- `ed25519-dalek`: 3.0.0 on crates.io (2026-07-06). 3.0 is new: API changes since 2.x unverified; check docs.rs. `VerifyingKey::verify_strict` (present in 2.x) rejects weak/small-order keys and non-canonical signatures, which is the right call for a fixed-key update check (https://docs.rs/ed25519-dalek).

## 3. Download

- RFC 9110 §14 (https://www.rfc-editor.org/rfc/rfc9110#section-14): `Range: bytes=a-b` gives `206 Partial Content`; `If-Range` with a strong ETag or Last-Modified avoids splicing two versions; `416` when unsatisfiable; a server may ignore Range and send 200 (client must handle).
- ours: with content-addressed block files or immutable versioned pack URLs, If-Range is moot; verify each block's blake3 before writing; resume = re-request missing blocks.
- Versions (crates.io, 2026-11-10): `reqwest` 0.13.5, `rustls` 0.23.46, `rustls-platform-verifier` 0.7.1, `ureq` 3.5.1.
- reqwest 0.13 reportedly made rustls the default TLS and uses the platform verifier by default (https://github.com/seanmonstar/reqwest/releases, unverified today). Pulls tokio + hyper.
- rustls-platform-verifier README (https://github.com/rustls/rustls-platform-verifier): uses Security.framework on Apple, the Windows cert APIs, and on Android a bundled Kotlin component via JNI; the app must ship that component (the crate ships a Maven-local repo to add in Gradle) and call an init with the JavaVM and Context at startup. ours: our hand-built Gradle/AAB pipeline must add it; this is a real task.
- ring vs aws-lc-rs: rustls defaults to aws-lc-rs, which needs a C/asm build (cmake/NASM on some targets) and has historically been harder for iOS/Android cross builds; `ring` is the lighter option. Unverified today.
- Binary size: no authoritative figure found; ours: reqwest+tokio+hyper+rustls typically adds a few MB; ureq 3 (sync, no tokio) is smaller. Measure with `cargo bloat`.
- ureq 3 (https://docs.rs/ureq): blocking, rustls default, supports platform verifier as an option per its docs (unverified). ours: a patcher thread doing blocking range GETs is enough; ureq avoids pulling tokio into the engine.
- Localhost test server: `tiny_http` 0.12.0 is unmaintained-looking (last release 2022-10-06). ours: a 100-line hand-written `std::net::TcpListener` server serving range requests from memory is simplest and also lets tests inject drops, short reads, wrong bytes and 200-ignoring-range. `hyper` works if tokio is already in.

## 4. Atomic swap

- POSIX `rename(2)` replaces the target atomically on the same filesystem (https://pubs.opengroup.org/onlinepubs/9699919799/functions/rename.html); for durability fsync the file, rename, then fsync the directory (LWN "ext4 and data loss", well known).
- Windows: `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING` (https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw), or `SetFileInformationByHandle` with `FileRenameInfoEx` + POSIX semantics on Windows 10 1607+; Rust's `std::fs::rename` uses replace semantics. Fails if the target is open without FILE_SHARE_DELETE (ours: a mmapped pack blocks replacing it).
- ours, recommended: never overwrite a pack in place. Write new packs under content-hashed names (`zone3.<hash>.spack`) next to old ones; when all verify, write `current.manifest.tmp`, fsync, rename over `current.manifest`, fsync dir. On launch read only `current.manifest`; garbage-collect unreferenced packs after the next successful launch. That is atomic on every OS and keeps the old version until the new one is proven.
- iOS: set `NSURLIsExcludedFromBackupKey` on downloaded content, or put it in `Library/Caches` (purgeable) / `Application Support` with the key set (https://developer.apple.com/documentation/foundation/optimizing-your-app-s-data-for-icloud-backup). ours: Application Support plus the key, since Caches can be purged under storage pressure.
- Background URLSession (https://developer.apple.com/documentation/foundation/downloading-files-in-the-background): `URLSessionConfiguration.background(withIdentifier:)`, download tasks only survive suspension, the app is relaunched via `application(_:handleEventsForBackgroundURLSession:completionHandler:)`, files land in a temp location that must be moved before the delegate returns. ours: few, large requests (pack or block bundle files, not per-block ranges) suit this; per-block ranges should stay foreground.
- Android: no direct equivalent; WorkManager or DownloadManager (Java-side). ours: defer; foreground download with resume is acceptable for M4.

## 5. Delta inside compressed packs

- bsdiff (Percival, https://www.daemonology.net/bsdiff/) needs O(n) memory on the old file and is slow on large inputs. zstd `--patch-from` (zstd 1.4.5+, https://github.com/facebook/zstd/wiki/Zstandard-as-a-patching-engine) claims patches near bsdiff size at far higher speed, using the old file as a dictionary, with a window bound by `--long`.
- ours: diffing compressed blocks is mostly useless (compressed bytes change wholesale). Diffing uncompressed assets with zstd patch-from could help for a few large, slightly edited assets (meshes, big tables), but doubles client work (decompress old, patch, recompress, re-hash) and complicates verify. Chunk reuse first; add per-asset zstd deltas only if measured patch sizes demand it.
- ours: textures in GPU block formats (BC/ASTC) change locally when re-encoded only if the encoder is deterministic; make cooks deterministic before worrying about deltas.
