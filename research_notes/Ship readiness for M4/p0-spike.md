# P0: what a patch costs

M4's spike P0 (m4-plan §4, track P), run on 2026-11-10 on the M5 (macOS, arm64) at 0755aafb, with other agents' builds, goldens and benches beside it (load averages 2 to 27). Everything here was built and run; nothing was read off the web but the crates' own docs and sources, fetched by cargo the same day. It answers three questions for P1 and P2: does a cook repeat itself, how many stored blocks one edit moves, and what `ureq` 3 with `rustls` and the platform verifier costs on the five targets.

## 1. A cook repeats itself, byte for byte

**Method.** The tools-profile `sapphire_pipeline` at 0755aafb cooked a copy of `content/` the way `cargo xtask content --locked` does (`cook --source … --out … --packs … --code <worktree> --cook <cook> --cache … --locked`, no generators), each time into new output directories with an empty cache. Three cold cooks per platform: two from one copy of the content, one from a second copy at another path, with fresh file times (`cp -R`).

**Result.** All three cooks of each platform are the same, byte for byte, across every file the cook ships: each pack, `NOTICES.txt` and `documents/` (`diff -r` of the pack directories). The source's path and its files' times don't reach the output. A cold cook took 17–20 s at load averages of 2 to 5.

| Cook | Packs | Bytes shipped | Largest packs |
|---|---|---|---|
| desktop | 11, plus `NOTICES.txt` and 4 documents | 37.8 MB | `shared` 19.7 MB, `zone_lantern_ward` 9.5 MB, `zone_town` 3.9 MB, `audio` 2.9 MB, `fonts` 2.5 MB |
| mobile | 11, plus the same | 27.2 MB | `shared` 15.7 MB, `zone_lantern_ward` 3.7 MB, `zone_town` 2.9 MB, `audio` 2.9 MB, `fonts` 2.5 MB |

That holds for one machine. It says nothing about a cook on another architecture or OS: texture encoders (BC7, ASTC through `ctt`), mesh optimization, simplification and the probe bake run floating point, and only the move bake is held to the same bytes everywhere (spec §5.22). See §4 for what that means for P1.

## 2. One edit moves its own blocks and nothing else

**Method.** One edit at a time to the copy, then a desktop and a mobile cook from the baseline's warm cache (a copy of the first cold cook's), compared with the first cold cook's packs. A cook repeats itself, and the cache's key covers every input, so a warm cook is the cold cook's bytes (one edit was also cooked cold to check: §2's last paragraph). Every edit was then put back, and the copy compared equal to `content/` at the end. No content edit is committed.

**What a client fetches**, as exit test 2 has it: the new manifest, the table of contents of each pack whose header changed, and every block whose blake3 no installed pack holds, once per hash. The manifest is estimated at 128 bytes plus 72 a pack (a name of up to 32 bytes, its size and its header hash, as §3's "What's signed" lists), 920 bytes for eleven packs. A pack's tables are its first `data_offset` bytes: the 256-byte header and its table of contents.

The edits, in the order run:

- **Texture:** `lookdev/sky/nebula.png` (2048 × 1024, the largest painted map in `shared`), a 64 × 64 square at (64, 64) inverted.
- **Mesh:** `lookdev/character/character.vrm`, the largest mesh in `shared`: its first primitive's first vertex moved halfway to its second (about 9 mm), inside the old bounds. Also **the boss**, `combat/knell_colossus/knell_colossus.glb`, the same way (about 7 cm).
- **Sound:** `audio/generated/music/lantern_bells.ogg`, regenerated by `sapphire_soundgen` with one note of the bells' tune changed (the third, 79 to 81), the generator's code put back after. The other eight files it writes came out identical to the committed ones.
- **String:** `title-tagline` in both `loc/en/game_ui.ftl` and `loc/ja/game_ui.ftl`.
- **Screen:** the title's tagline style in `ui/title.ui.ron`, size 18 to 20. Also **the screen list**, `ui/menus.ron`, a comment added to one row.
- **Zone placement:** one of the four lantern posts around the Gate Square (`lantern_ward.zone.ron`, `at: (12.0, 0.0, -13.0)`) moved 0.5 m along x.

Blocks are each cook's stored blocks; "kept" counts the edited pack's blocks whose hash the old pack holds, by count and by stored bytes. Every other pack came out byte for byte the same after every edit. "Fetch" is new blocks, plus tables of changed packs, plus the 920-byte manifest. "Asset" is the edited asset's own stored bytes in the new pack (D desktop, M mobile).

**Where the bytes go.**

- **No edit moved another asset's blocks.** Every pack an edit didn't reach came out byte for byte the same, and in the pack it did reach, every block outside the edited asset kept its hash. An asset whose size changes moves the offsets of the blocks after it, which changes the pack's block table, but not their bytes or hashes. That is the property §3's "What a patch moves" leans on, and it holds.
- **A texture edit is local.** The 64 × 64 square changed 5 of the map's 43 blocks (12 %), as many as the block-compressed rows holding it in each mip level need, on both BC7 and ASTC. The rest of the map kept its bytes.
- **A mesh edit is the whole mesh.** Moving one vertex of the character changed every one of its 41 blocks on desktop (29 on mobile), and the boss's 4 of 4. Desktop's first 64 KiB differed in 43,164 bytes, and every block after it in between 4,300 and 63,000: the change is spread through the file, not a shift from one point. The likely cause, read from `optimize.rs` and not traced: the simplifier's LOD chain depends on every position, vertices are ordered by the coarsest LOD that first uses them, and triangles by cache and overdraw, so one moved vertex can reorder the streams and the indices. The cooked size moved by 36 bytes on desktop and 72 on mobile.
- **CDC wouldn't save that mesh.** The same two cooked meshes, chunked by a gear-hash CDC (FastCDC's shape: 2 KiB minimum, about 8 KiB average, 64 KiB maximum, over the uncompressed cooked bytes, in a throwaway script), share 18.6 % of the character's bytes on desktop and 12.3 % on mobile, and 5.2 % and 4.7 % of the boss's, against 0 % for fixed 64 KiB blocks. 46–71 % of each file's bytes are equal at the same offset, scattered too thinly for any chunking to keep. CDC would save at most a fifth of a mesh's patch, at the price §3 names: chunking uncompressed data and compressing again on the client.
- **The tables are most of a small patch.** A changed pack's table of contents is fetched whole: 122,720 bytes for `shared` on desktop, 55,920 for `zone_lantern_ward`, 40,880 for `audio`. For the texture that's 42 % of the patch, and for the placement, the boss and the sound more than the blocks themselves. It is still at most 123 KB a pack, against a cook of 27–38 MB.
- **A placement moves a cell's mesh, not the zone.** Moving a lantern post rebuilt the one merged mesh of its cell (8,592 bytes cooked) and nothing else: the zone document, its colliders, navmesh and probe grid kept their bytes. The cell's merged geometry is presentation, as §3 wants a zone's look to be. The colliders didn't follow the post, which is the content's business, not the patcher's.
- **A string edit moves every locale's table it touches.** Both tables are one block each, so the edit fetched all of `loc` but its header: 6 KB.
- **The screen list isn't in a pack.** `ui/menus.ron` ships as a loose file under `documents/`, copied as it is (comments included), so its edit changed no pack. See §4.

**Warm cooks are cold cooks.** The texture edit was also cooked from an empty cache (49 s under load): its packs are byte for byte the warm cook's.

## 3. ureq 3, rustls on ring and the platform verifier

**Method.** A throwaway crate outside the workspace, on the workspace's toolchain (1.99.0): a library with `fetch(url)`, which with the feature on builds a `ureq::Agent` with `TlsProvider::Rustls`, `RootCerts::PlatformVerifier` and `rustls::crypto::ring::default_provider()` and makes one GET with a `Range` header, and without it returns the URL's length. A binary calls it, and on Android an exported `extern "C"` entry takes a raw `JNIEnv` and context, as SDL hands them over, and runs `rustls_platform_verifier::android::init_with_env` first. The crates cargo chose: `ureq` 3.5.1 (`default-features = false`, features `rustls-no-provider` and `platform-verifier`), `rustls` 0.23.46 (`ring`, `std`, `tls12`, `logging`), `ring` 0.17.14, `rustls-platform-verifier` 0.7.1, `rustls-webpki` 0.103.16, and on Android `jni` 0.22.4 (the version already in our `Cargo.lock`) and `rustls-platform-verifier-android` 0.2.0. No `aws-lc-rs`, `tokio` or `hyper`, and with `rustls-no-provider` no `webpki-roots`.

**Builds.** `cargo check --target` with and without the feature:

| Target | Without | With |
|---|---|---|
| aarch64-apple-darwin | builds | builds |
| aarch64-apple-ios | builds | builds |
| aarch64-linux-android (NDK 29.0.14206865, API 29 clang) | builds | builds |
| x86_64-unknown-linux-gnu | builds | **not checked here**: `ring`'s build script compiles C and finds no `x86_64-linux-gnu-gcc` or Linux sysroot on this Mac |
| x86_64-pc-windows-msvc | builds | **not checked here**: `ring`'s C finds no MSVC headers (`assert.h`) on this Mac |

The two failures are this Mac's missing C cross toolchains, not the crates: CI's Linux and Windows runners have native compilers, and P2's first CI run is the proof. The `ring` provider builds with the target's ordinary C compiler and its pregenerated assembly, with no CMake, NASM or Go; on Apple targets that is Xcode's clang, on Android the NDK's, and neither needed a setting beyond what xtask already gives cargo.

**Bytes added.** A shipping-like profile (`lto = "fat"`, `codegen-units = 1`, `panic = "abort"`, symbols stripped), sizes in bytes:

| Target | Artifact | Without | With one HTTPS GET | Added |
|---|---|---|---|---|
| aarch64-apple-ios | binary | 299,280 | 1,435,512 | 1,136,232 (1.08 MiB) |
| aarch64-apple-darwin | binary | 302,272 | 1,447,408 | 1,145,136 (1.09 MiB) |
| aarch64-linux-android | binary | 277,216 | 1,631,144 | 1,353,928 (1.29 MiB) |
| aarch64-linux-android | `cdylib` with the JNI entry and `init_with_env` | 299,240 | 1,843,144 | 1,543,904 (1.47 MiB) |

The Android library is the shape the game ships (one `.so`, `max-page-size=16384`). These are the cost against a near-empty program; inside `game_app` the share of `std` and anything else already linked will be smaller, so read them as an upper bound. Against the game's 27.5 MB release binary (M3 S2) it is about 4–6 %.

**What Android's verifier needs.** From the crate's README and source (0.7.1, read 2026-11-10 in cargo's registry cache):

- **A Kotlin component in the APK.** Verification calls `org.rustls.platformverifier.CertificateVerifier` through JNI, loaded by the app's class loader. It isn't in the crate: `rustls-platform-verifier-android` 0.2.0 has no files but an empty `lib.rs` and exists so that `Cargo.lock` carries the component's version. The component is a prebuilt AAR that the README says to fetch from a Maven repository the project serves from GitHub (`https://github.com/rustls/rustls-platform-verifier/raw/maven-archive/android-release-support/maven/`), as `rustls:rustls-platform-verifier`, with a Gradle `ValueSource` that reads the version from `Cargo.lock` and pins it, because "runtime crashes may occur" on a mismatched version. That is a download at Gradle time. Our Gradle builds run `--offline` and agents download nothing, so the AAR isn't in this Mac's Gradle cache, and what it pulls in (Kotlin's standard library, at least, if the AAR's POM names it) is unverified.
- **Gradle wiring** in `platform/android/app/build.gradle.kts`: the Maven repository (or a local copy), the `ValueSource` and resolution rule, and `implementation("rustls:rustls-platform-verifier")`. `settings.gradle.kts` sets `RepositoriesMode.FAIL_ON_PROJECT_REPOS`, so the repository goes in `settings.gradle.kts`'s `dependencyResolutionManagement`, not the app's.
- **R8 or ProGuard:** a keep rule, `-keep, includedescriptorclasses class org.rustls.platformverifier.** { *; }`, since nothing on the Java side calls the class. The release build doesn't minify today; a store build that does needs it.
- **Initialization before any TLS:** `init_with_env(&mut Env, context)` (or `init_with_refs`, `init_with_runtime`) once per process, with a `Context`. Without it, the first verification panics (`android::global()` is an `expect`). SDL's `SDL_GetAndroidJNIEnv` and activity are enough; the activity itself needs no change. It compiled against `jni` 0.22's `EnvUnowned::with_env`, which catches a panic at the boundary.
- Revocation needs API 24; the game's minimum is 29.

**For P2's tests:** ureq's `RootCerts::Specific` takes a test root, so a localhost TLS server in a test can be trusted without touching a trust store, and `RootCerts::PlatformVerifier` against the same server shows the platform refusing it. ureq's default is `RootCerts::WebPki`, so P2 sets the platform verifier explicitly.

## 4. What this means for the plan

- **Block-level patching holds; CDC isn't needed.** No edit shifted another asset's blocks, and every patch here was the edited asset's own blocks plus at most 123 KB of tables, 3 % of a cook at worst. The one case where blocks do poorly, a mesh, is the cooker reordering the whole mesh, which CDC recovers less than a fifth of. If mesh patches ever matter, the lever is the mesh cooker's order (a vertex order that one moved vertex doesn't reshuffle), not the patcher. §3 stands as written.
- **P1 needn't make cooks repeat on one machine: they do.** Two things it should still hold:
  - **What holds it.** Each stage has its own test (`cooks_are_deterministic` in `cook.rs`, `optimizing_is_deterministic`, `texture_cooks_are_deterministic_and_keyed_by_their_settings`, `bakes_are_deterministic` for probes, `packing_is_deterministic_and_cached`). Nothing holds the whole tree, or two machines: CI could cook `--locked` on Linux and compare the packs' hashes with a macOS cook's, which would say whether a release can be cooked anywhere.
  - **One machine cooks releases**, or the manifest names that machine's architecture, until a cross-machine comparison says otherwise. A release cooked on another architecture may re-encode every texture and mesh, and a patch would then carry them all.
- **`documents/` ships outside the packs.** The game's flow, flags and screen list (`game.documents.ron`, `game.flow.ron`, `flags.ron`, `ui/menus.ron`) are loose files beside the packs, so the manifest as §3 has it (packs' names, sizes and header hashes) doesn't cover them: a patch couldn't move them, and a tampered one would mount. P1 should name each with its size and blake3, or pack them. Which of them a patch may carry is §3's "What a patch may carry" to answer: the screen list is presentation, the flow and flags are arguably what the simulation reads.
- **Android's verifier needs an AAR from outside.** For P2 or S3 (`google-play`): the maintainer fetches `rustls-platform-verifier`'s AAR for the locked version once into a Maven directory in the repository (MIT or Apache-2.0, so it can be committed with its provenance), and Gradle reads it offline; or the Gradle build goes online for that one repository. Either is the orchestrator's call. Until then an Android build can initialize the verifier but not verify a certificate: loading the class fails, and every TLS handshake with it.
